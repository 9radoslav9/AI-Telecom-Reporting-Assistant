# AI Telecom Reporting Assistant

**Не вярвай сляпо на AI — провери го.**

Асистент за автоматизирано отчитане на телеком бизнес данни: агрегира реални данни от база данни, кара LLM да напише резюме на естествен език, и **програмно проверява всяко число в резюмето срещу оригиналните данни**, преди потребителят изобщо да го прочете.

🔗 **Живо демо:** [ai-telecom-reporting-assistant.streamlit.app](https://ai-telecom-reporting-assistant.streamlit.app/)

📂 **Repo:** [github.com/9radoslav9/AI-Telecom-Reporting-Assistant](https://github.com/9radoslav9/AI-Telecom-Reporting-Assistant)

## Защо този проект съществува

LLM-ите пишат гладко и звучат уверено — включително когато грешат. За бизнес отчитане, където числата отиват при мениджъри и вземат решения, "звучи убедително" не е достатъчно добър стандарт.

Този проект е малка, но напълно работеща демонстрация на друг подход: LLM-ът върши това, в което е добър (превръща сурови данни в четим текст), а детерминистичен Python код върши това, в което LLM-ът **не бива** да се доверява сляпо — проверка на всяко число.

Не е теоретично твърдение. По-долу в този README има документирани случаи, в които моделът реално е сгрешил — хванати именно от тази проверка.

## Как работи (архитектура)

```
┌─────────────┐    ┌──────────────┐    ┌─────────────┐    ┌────────────┐    ┌──────────────┐
│   Supabase  │───▶│ aggregation  │───▶│ formatting  │───▶│    LLM     │───▶│ verification │
│ (PostgreSQL)│    │    .py       │    │    .py      │    │   .py      │    │     .py      │
│ SQL функции │    │ .rpc() extract│   │ dict → текст│    │ OpenRouter │    │ число в текст?│
└─────────────┘    └──────────────┘    └─────────────┘    └────────────┘    └──────────────┘
                                                                                     │
                                                                                     ▼
                                                                          ┌────────────────────┐
                                                                          │   Streamlit app.py  │
                                                                          │ данни + резюме + ✅/⚠️│
                                                                          └────────────────────┘
```

Всичко е обединено в **`pipeline.py`**, чиято функция `run_pipeline(question)` минава автоматично през целия синджир за избрания въпрос (`"revenue"`, `"customers"` или `"usage"`) и връща структуриран резултат — суровите данни, LLM резюмето и verification резултата, накуп.

### Защо агрегацията е в SQL, не в Python

Трите агрегационни заявки (`revenue_by_region`, `new_customers_by_month`, `usage_by_plan`) са PostgreSQL функции, живеещи директно в Supabase, извиквани от Python само през `.rpc()`. Съзнателен избор по две причини:

1. **SQL агрегацията е по-евтина и по-контролирана** — LLM-ът получава готови, малки, обобщени числа, вместо да му се подават стотици сурови редове и да се разчита той да смята върху тях.
2. Показва SQL умения (JOIN-ове, CTE, `GROUP BY`, агрегатни функции) като видими, версионирани артефакти в repo-то (`SQL/aggregations.sql`), а не скрита логика.

### Защо няма free-form text-to-SQL

Съзнателно решение: потребителят не пише свободен въпрос, който LLM-ът превръща в SQL заявка. Вместо това има три фиксирани, предварително тествани въпроса. Причина: неконтролируем AI-генериран SQL, изпълняван директно срещу база данни, е точно обратното на наратива "не вярвай сляпо на AI" — вместо да проверяваш изхода, би се доверявал на модела да напише безопасен и коректен код на всяка стъпка.

## Компоненти

| Файл | Отговорност |
|---|---|
| `database.py` | Connection setup към Supabase (3 реда логика) — нищо друго |
| `SQL/aggregations.sql` | Трите `CREATE OR REPLACE FUNCTION` дефиниции, версионирани за проследимост |
| `aggregation.py` | Тънък Python wrapper — извиква SQL функциите през `.rpc()`, никаква groupby логика в Python |
| `formatting.py` | Превръща суровите dict списъци в чист текст за LLM prompt-а (по-евтино откъм токени, по-предвidimо за verification) |
| `LLM.py` | OpenRouter клиент (`requests`), `SYSTEM_PROMPT` с 8 строги правила, `generate_summary()` |
| `verification.py` | `verify_summary()` — сравнява директно подадените стойности от агрегациите срещу текста на резюмето |
| `pipeline.py` | `run_pipeline(question)` — обединява всичко, използва се от UI-то |
| `app.py` | Streamlit UI — избор на въпрос, таблица с данни, LLM резюме, verification резултат с ✅/⚠️ |
| `seed_data.py` | Генериране на synthetic данни (Faker) — напълно изолиран, никога не се импортва от активния pipeline |

## Verification — как точно работи проверката

```python
def verify_summary(data, summary_text, fields_to_check):
    results = []
    for row in data:
        for field in fields_to_check:
            expected_text = str(row[field])
            status = "намерено" if expected_text in summary_text else "липсва"
            results.append((row, field, status))
    return results
```

Проста, обяснима логика: за всяка стойност, която агрегацията реално е върнала (напр. приход на регион), проверява дали точно тази стойност се среща в текста на LLM резюмето. Резултатът се показва в Streamlit-а като таблица с ✅ ("намерено") или ⚠️ ("липсва") за всяко поле.

### Съзнателно ограничение на обхвата

`verification.py` проверява **само директно подадени** стойности от агрегациите — не пресмята и не сверява изведени статистики (сума, средно аритметично, брой елементи под граница), които LLM-ът евентуално спомене сам. Това е умишлен избор, не пропуск, обоснован директно от реални тестове (виж секцията по-долу): моделът е надежден "преразказвач" на подадени числа, но ненадежден "калкулатор" — и точно тази граница системата е проектирана да следи.

Разгледан е и по-задълбочен подход (Python предварително смята производни стойности и ги сверява), но е съзнателно отхвърлен като излишна сложност за обхвата на този проект — по-простата версия покрива реалния риск, доказан от тестовете.

**Важно уточнение:** verification механиката е независима, детерминистична Python логика — обикновен `in` string match, без AI преценка на който и да е етап. LLM-ът пише резюмето; Python го проверява.

## Хванати LLM грешки — доказателството зад наратива

По време на реално тестване, verification слоят улови конкретни грешки на модела:

| # | Агрегация | Твърдение на LLM | Реална стойност | Тип грешка |
|---|---|---|---|---|
| 1 | — | "индустрият" вместо "индустрията" | — | Граматична |
| 2 | `revenue_by_region` | Средно 110.69 € за 27 региона | 110.11 € | Грешно изчислено средно |
| 3 | `new_customers_by_month` | Общо 96 нови клиента | 100 | Грешна обща сума |

**Общ модел на грешките:** и в двата числови случая грешката се появява **единствено** когато моделът трябва сам да пресметне нещо (средно, сума) върху множество стойности. Контролен тест с `usage_by_plan` — данни, изискващи само директно преразказване без изчисление — излезе изцяло точен. Точно това наблюдение е причината `verification.py` да е ограничен по обхват както е описано по-горе: границата на доверие не е "дали LLM-ът греши", а конкретно "кога" — при агрегация на числа, не при преразказ на подадени числа.

## System Prompt — итеративно затягане

`SYSTEM_PROMPT` в `LLM.py` мина през три версии, всяка коригирана след реален проблем, открит чрез verification:

- **v1** — базови правила (само български, само подадени числа, без markdown). Резултат: моделът обобщаваше с диапазони ("региони между 165 и 176 лв.") вместо да цитира точни стойности → слабо verification покритие.
- **v2** — добавени правила: цитирай точното число (не диапазон); не пресмятай сам суми/средни/бройки. Рязко подобрение в точността.
- **v3 (текуща)** — правилото "не давай мнения" беше премахнато и заменено с контролирано разрешение за **едно** качествено бизнес наблюдение накрая, изрично забранено да съдържа числа. Резултат: полезен бизнес коментар без риск от нова, непроверена цифра.

Отделен реален бъг, хванат и коригиран по същия начин: моделът продължаваше да пише "лв." вместо "€" дори след като данните вече бяха в евро — класически пример за LLM, който "поправя" по training bias вместо да преразказва точно подаденото. Разрешено с изрично, категорично правило в prompt-а, вместо да се разчита на имплицитно копиране на символа.

## Технологичен стек

- **Python** — цялата бизнес логика и pipeline
- **Supabase (PostgreSQL)** — база данни + SQL агрегационни функции
- **OpenRouter** (`minimax/minimax-m3:free`) — LLM достъп през чист `requests`, без допълнителни SDK абстракции
- **Streamlit** — UI слой, deploy-нат чрез Streamlit Community Cloud
- **Faker** — генериране на synthetic данни (изолирано в `seed_data.py`)

### Защо `minimax/minimax-m3:free`

Изборът е направен емпирично, не теоретично — чрез реално сравнение на качеството на българския език между няколко безплатни модела на OpenRouter (включително по-голям reasoning модел, `nvidia/nemotron-3-ultra-550b-a55b`, който се оказа ненужно тежък за проста data-to-text задача).

## Съзнателни технически решения 

Проектът следва принцип: всяко решение трябва да може да бъде напълно обяснено на интервю, не просто да работи.

- **Без retry логика за rate limits (429)** — първи опит с retry+`sleep` беше отхвърлен като излишна сложност за обхвата на проекта.
- **String matching, не regex, във verification-а** — тестовете показаха, че моделът винаги преписва подадените числа точно; regex + толеранс за закръгляне би решавал проблем, който на практика не се случва.
- **`seed_data.py` напълно изолиран** от активния pipeline (никога не се импортва от `app.py`/`pipeline.py`/`aggregation.py`) , научен урок от реален инцидент по-долу.

## Инциденти, от които е научено (и решени правилно)

### Дублирани данни от module-level import код
Ранна версия на `database.py` държеше insert логиката на module level. Всеки `import` (включително индиректен, през веригата `main.py → aggregation.py → database.py`) е изпълнявал insert-ите наново — довело до утрояване на данните в базата. Разрешено с прецизни `DELETE` заявки и преработка на insert логиката в именувани функции.

### Изтекъл API ключ в git история
Стар закоментиран тестов код в `main.py` съдържаше реален OpenRouter ключ, изписан директно в текста (не през `.env`), вече push-нат в GitHub. Ключът е ротиран незабавно, старото repo е изтрито, ново чисто repo е инициализирано от нула. Резултатът е видим в самата git история на проекта — оставен нарочно като доказателство за коректна реакция при инцидент със сигурността, не заличен.

### Faker импорт, чупещ чист install
При финален преглед преди push беше открито, че `database.py` съдържаше module-level `from faker import Faker`, докато `faker` не е бил в `requirements.txt` — на чист `pip install`, точно сценарият на Streamlit Cloud deploy, приложението би гръмнало с `ModuleNotFoundError`. Разрешено чрез пълно извеждане на seed логиката в изолирания `seed_data.py`.

## Локално стартиране

```bash
git clone https://github.com/9radoslav9/AI-Telecom-Reporting-Assistant.git
cd AI-Telecom-Reporting-Assistant
pip install -r requirements.txt
```

Създай `.env` файл в root-а със следните променливи:

```
OPENROUTER_API_KEY=твоят_openrouter_ключ
SUPABASE_URL=твоят_supabase_url
SUPABASE_KEY=твоят_supabase_anon_key
```

Стартирай:

```bash
streamlit run app.py
```
