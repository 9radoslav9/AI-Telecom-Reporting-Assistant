# AI Telecom Reporting Assistant

**Автоматизиран телеком репортинг асистент — агрегира бизнес данни, кара LLM да напише резюме на естествен език, и после проверява всяко число в резюмето срещу реалните данни, преди да му повярва.**

🔗 [Живо демо](https://ai-telecom-reporting-assistant.streamlit.app) · 💻 [GitHub repo](https://github.com/9radoslav9/AI-Telecom-Reporting-Assistant)

## Централният наратив — не вярвам сляпо на AI

LLM-ите грешат по предвидим начин: преразказват точно подадени числа безпогрешно, но грешат щом трябва сами да пресметнат нещо (сума, средно, брой елементи под граница). Този проект е изграден около това наблюдение — генерира резюмета с LLM, но никога не приема съдържанието им на доверие. Всяко число в резюмето минава през независима, детерминистична Python проверка срещу оригиналните агрегирани данни, преди да се покаже като "потвърдено".

## Архитектура — фиксирани въпроси

```
   Supabase (PostgreSQL функции)
          │
          ▼
   aggregation.py  (.rpc() wrapper-и)
          │
          ▼
   formatting.py   (dict → чист текст)
          │
          ▼
   LLM_langchain.py → generate_summary()   (LangChain, ChatOpenRouter)
          │
          ▼
   verification.py → verify_summary()      ✅ намерено / ⚠️ липсва
          │
          ▼
   Streamlit UI
```

Три фиксирани бизнес въпроса (`revenue`/`customers`/`usage`), всеки минаващ през идентична верижка — routing-ът между тях е обикновен `if/elif` в `pipeline.py`, съзнателно без framework, защото пътищата са три, известни предварително и никога не се променят.

## Архитектура — свободен въпрос (V2)

```
   свободен текст
          │
          ▼
   ┌─────────────┐
   │  classify   │   LangChain chain — решава категорията
   └──────┬──────┘
          │
   revenue / customers / usage         general
          │                               │
          ▼                               ▼
   ┌─────────────┐                 ┌─────────────┐
   │    fixed    │                 │     rag     │
   │ (pipeline.  │                 │ (Qdrant +   │
   │ run_pipeline)│                 │ HuggingFace)│
   └──────┬──────┘                 └──────┬──────┘
          │                               │
          └───────────────┬───────────────┘
                           ▼
                      Streamlit UI
```

`agent.py` е LangGraph `StateGraph` с три node-а. `fixed` не разбива логиката наново — вика директно вече проверения `pipeline.run_pipeline()` като един node, нулево дублиране. LangGraph е ограничен изцяло до този слой — самият `pipeline.py` routing остава недокоснат чист Python, защото framework там не би добавил нищо, освен сложност.

## Защо агрегациите са SQL функции, не Python groupby

И трите бизнес агрегации (`revenue_by_region`, `new_customers_by_month`, `usage_by_plan`) са `CREATE OR REPLACE FUNCTION` дефиниции, версионирани в `SQL/aggregations.sql`, извиквани през `.rpc()`. Съзнателен избор — демонстрира SQL уменията директно като видими, четими repo артефакти, вместо да ги скрие зад Python логика.

## Защо не free-form text-to-SQL

Разгледан и отхвърлен подход: да се остави LLM-ът сам да генерира SQL заявки от свободния текст на потребителя. Отхвърлено съзнателно — неконтролируем AI-генериран SQL пряко противоречи на централния наратив "не вярвам сляпо на AI". Вместо това свободните въпроси минават през класификация към позната, вече проверена агрегация, или през RAG с прозрачно показани източници — никога през AI, който сам решава каква заявка да пусне срещу базата.

## Данните

Synthetic телеком данни, генерирани с Faker (`bg_BG` locale), в Supabase:
- `plans` — 3 реда (Basic, Standard, Premium)
- `customers` — 100 реда, разпределени по 27 български административни региона
- `usage_records` — 400 реда (100 клиента × 4 месеца назад)

## Verification слой

```python
def verify_summary(data, summary_text, fields_to_check):
    results = []

    for row in data:
        for field in fields_to_check:
            expected_value = row[field]
            expected_text = str(expected_value)

            if expected_text in summary_text:
                status = "намерено"
            else:
                status = "липсва"

            results.append((row, field, status))

    return results
```

Съзнателно ограничен обхват — проверява само **директно подадени** стойности от агрегациите (напр. `total_revenue` за всеки регион), не изведени/пресметнати от LLM-а величини (средно, сума). Емпирично установено: моделът никога не греши при преразказ на подадени числа, греши единствено когато сам пресмята нещо върху много стойности — затова verification слоят е насочен точно там, където реалният риск е.

## Хванати LLM грешки

| # | Модел | Данни | LLM твърдение | Реална стойност |
|---|---|---|---|---|
| 1 | nemotron-3-ultra | — | "индустрият" (грешен член) | "индустрията" |
| 2 | minimax-m3 | revenue by region, 27 региона | средно 110.69 € | 110.11 € |
| 3 | minimax-m3 | new customers by month | общо 96 нови клиента | 100 |

Контролен случай (`usage_by_plan`, стойности директно подадени, без нужда от изчисление) — всички числа точни. Моделът е надежден "преразказвач" на подадени числа, но ненадежден "калкулатор" — точно тази граница `verification.py` е проектиран да следи.

### Допълнителен случай — грешка в собствения ми routing дизайн, не в модела

При тестване на свободния въпрос след първата версия на `agent.py` се появи различен тип проблем: почти всеки въпрос, съдържащ дума като "приходи"/"клиенти"/"данни", се насочваше към фиксираната справка — дори въпроси, изискващи реално разсъждение ("кой регион печели най-много"). Причината: първоначалният класифициращ промпт описваше категориите по **тема**, не по това дали въпросът буквално иска пълната фиксирана справка. Едновременно с това RAG отговорите почти винаги отказваха с "нямам данни" при по-общи въпроси, защото `top_k=3` покриваше твърде малка част от малкия корпус (~53 документа), а промптът инструктираше строг отказ при непълен контекст.

И двете бяха хванати чрез директно тестване на реалното поведение на системата, не чрез преглед на кода — заостри се класифициращият промпт с изрични примери за разликата "буквална справка" срещу "изисква разсъждение", вдигна се `top_k` на 6, и се омекоти условието за отказ в RAG промпта (отговаря на частичен, но релевантен контекст, вместо да отказва при всяка непълнота). Директно приложение на същата "не вярвам сляпо" дисциплина — този път насочена към собствения ми prompt/routing дизайн, не само към крайния текст на модела.

## Еволюция на SYSTEM_PROMPT-а

Резюметата минаха през три версии, докато не станаха достатъчно дисциплинирани:
- **v1** — базови правила; резултат: точни числа, но модела обобщаваше с диапазони вместо конкретни стойности
- **v2** — добавени правила: цитирай точното число вместо диапазон, не пресмятай сам суми/средни
- **v3** (финална) — премахнато "не давай мнения", заменено с разрешение за точно едно качествено бизнес наблюдение накрая, без числа

Отделен, реален бъг: след преминаването на България към еврото, данните и промптовете бяха обновени от "лв." на "€", но LLM-ът продължи да пише "лв." — моделът "нормализираше" по training bias към по-позната му дума. Фиксирано с изрично, категорично правило в промпта, вместо разчитане на имплицитно копиране на символа от данните.

## RAG архитектура — изцяло облачна

| Компонент | Услуга | Роля |
|---|---|---|
| LLM | OpenRouter (`inclusionai/ling-3.0-flash-vl:free`) | Генерира резюмета и RAG отговори |
| Embeddings | HuggingFace Inference API, `intfloat/multilingual-e5-large` | Текст → 1024-мерен вектор (многоезичен модел — данните и въпросите са на български) |
| Vector DB | Qdrant Cloud | Съхранение и семантично търсене |

Архитектурата е съзнателно изцяло в облака — три различни управлявани услуги, комбинирани вместо едно локално парче инфраструктура, зависимо от конкретната машина.

Всеки ред от трите агрегации се превръща в едно изречение (`row_to_text()`) и се индексира като отделна точка в Qdrant — "chunking" стратегията е естествена за структурирани таблични данни, не изкуствено нарязване на дълъг текст. Индексът се пресъздава изцяло при всяко обновяване (`collection_exists → delete → create`), същия принцип като `CREATE OR REPLACE FUNCTION` в SQL-а.

## LangChain / LangGraph — къде и защо точно там

- **LangChain е production за цялата LLM генерация** — резюмета за трите фиксирани въпроса, RAG отговори, и класификация на свободни въпроси, всичките през `ChatOpenRouter` в `LLM_langchain.py`. Първоначално написан ръчно с чист `requests` (виж git история, tag `v1.0`), после съзнателно заменен, след като framework-ът показа реална стойност — стандартизиран речник, по-малко ръчна поддръжка на HTTP/parsing логика.
- **`requests` остава** единствено за HuggingFace embedding извикванията в `rag.py` — прост HTTP слой без нужда от допълнителен SDK.
- **LangGraph е ограничен изцяло до `agent.py`** — routing-ът за свободния въпрос е единственото място в проекта, където пътят реално не е известен предварително. Фиксираният `if/elif` в `pipeline.py` остава недокоснат — framework там би добавил сложност без реална полза, точно обратното на целта.

## Технологичен стек

- **Език/framework:** Python, Streamlit
- **База данни:** Supabase (PostgreSQL), достъп през `supabase-py` и `.rpc()`
- **LLM:** OpenRouter, през LangChain (`langchain-openrouter`)
- **Vector search:** Qdrant Cloud (`qdrant-client`)
- **Embeddings:** HuggingFace Inference API
- **Agent orchestration:** LangGraph
- **CI/CD:** GitHub Actions
- **Deployment:** Streamlit Community Cloud

## Съзнателни решения за простота

- Без retry/error handling логика за rate limiting — прекалено сложно за нивото и типа на проекта, съзнателно оставено просто
- Просто `in` текстово съвпадение за verification, не regex с толеранс — данните показаха, че моделът винаги преписва числата точно както са подадени
- Без версийни pin-ове в `requirements.txt`, с изключение на `langchain-openrouter`/`langchain-core` — пиннати изрично, защото пакетът е официално маркиран "beta, moves fast"
- `seed_data.py` напълно изолиран от активния pipeline (guard-нат с `if __name__ == "__main__":`) — seed логиката никога не може да засегне production кода или да счупи чист install

## Инциденти, от които е научено

- **Дублирани данни** — некоментирана insert логика на module level се е изпълнявала повторно при всеки `import` (`plans` от 3 на 12 реда, `customers` от 100 на 250). Фиксирано с преместване в guard-нати функции, изолирани в `seed_data.py`
- **Липсващ пакет в `requirements.txt`** — `database.py` съдържаше активен `faker` import на module level, докато `faker` липсваше от `requirements.txt`; би счупило чист install (`ModuleNotFoundError`) точно при deploy. Хванато при ръчен преглед, после автоматизирано в CI (`import app` стъпка)
- **Собствен routing дизайн бъг** — виж секцията по-горе за класификатора, объркал тема с буквална заявка

## CI/CD

`.github/workflows/ci.yml` тества на всеки push/PR към `main` и `v2-dev`:
1. Чист `pip install -r requirements.txt`
2. Двустъпков `flake8` — критични грешки спират build-а, пълен стилов доклад е само информативен
3. `python -c "import app"` — автоматизирана версия на ръчния `faker` bug preview: ако някой файл ползва пакет, липсващ от `requirements.txt`, тази стъпка гърми веднага, вместо да чака ръчен review

## Версия и еволюция

`main` branch е стабилен, публично deploy-нат. Историята на проекта е маркирана с git tag `v1` — версията с чист `requests`, фиксирани три въпроса, без RAG/agent слой. Цялата V2 работа (LangChain production смяна, RAG, LangGraph агент) се разви на отделен `v2-dev` branch, merge-нат в `main` едва след пълно локално тестване и потвърден зелен CI. Съзнателна стратегия за управление на риска около живото demo, докато се въвеждат нови framework-и.
